# M1 — Behavior Cloning: "Beat Random" (and what that gate got wrong)

**Date:** 2026-07-08
**Status:** ✅ Complete — BC agent **exceeds** its teacher; submitted to Kaggle
(submission 54444045, `M1: behavior-cloned ... (bc_v1)`).
**Plan:** [M1-plan.md](M1-plan.md) (two-stage: prove pipeline on current encoders, then enrich and retrain)

## What M1 was about

M0's agent played legally but lost ~100% to `random` — random weights encode an arbitrary,
consistent, terrible policy. M1 replaced those weights with a policy trained by
**behavior cloning**: record the rule-based Mega Lucario sample agent playing itself,
then train `OptionScorer` (supervised, cross-entropy) to pick the same moves. Piotr wrote
the training core — his first real torch training loop — with Claude building the
collection/eval/gate infrastructure around it.

## How it works (one paragraph)

1,000 teacher self-play games via the direct engine loop → 46k decisions, each stored as
(encoded state, encoded option menu, index the teacher picked, final ±1 result). A
`Dataset`/`collate` pair batches the variable-length menus by padding + boolean mask;
the loss masks padded slots to −1e9 and applies cross-entropy ("how surprised was the
model by the teacher's move"), plus a small Huber loss training the value head against
the final result (a free critic warm start for M2). Best-validation-accuracy checkpoint
gets exported through the existing parity-gated pipeline into the numpy submission.

## Results

| Matchup | Win rate | Notes |
|---|---|---|
| M0 random-weights vs `random` | ~0% | the baseline we started from |
| **Teacher** (rule-based Lucario) vs `random` | **88%** (n=100) | the cloneable ceiling |
| BC v0 (Stage A encoders) vs `random` | 91% (n=100) → **81% (n=300)** | statistically ~teacher-level |
| BC v1 (Stage B encoders) vs `random` | **90.0% (n=300)** | +9pp over v0 at equal sample size |
| BC v1 vs teacher | **70% (n=100)** | see the slot-advantage caveat below |

**The student beats its teacher.** Caveat measured, not hand-waved: our agent occupied
the player-0 slot, and teacher-mirror games show a **~61% player-0 advantage** — so the
fair-slot read is roughly "+10pp above parity," not +20. Still: a cloned policy that
*generalizes* can outplay the rules it was cloned from.

Validation top-1 accuracy (how often the model's top pick = teacher's pick on held-out
games): Stage A **90.9%** (peaked epoch 5 of 10). Stage B: **90.4%** (epoch 8) —
*unchanged*, despite the win rate jumping. See lesson 7.

**Behavioral fingerprint** (take-rate per option type in MAIN decisions) — the clearest
before/after evidence. M0 took the ATTACH action 2 times out of 1,439 offers; BC v0:

| OptionType | Teacher | BC v0 |
|---|---|---|
| ATTACH | 11% | 8% |
| ATTACK | 21% | 16% |
| PLAY | 50% | 61% |
| EVOLVE | 33% | 33% |
| ABILITY | 100% | 40% ← biggest remaining imitation gap |
| RETREAT | 0% | 0% |

## Stage B: what changed and why

Stage A's overfit test exposed the encoder ceiling precisely: **337 of 500 sampled menus
contained two options that encoded to identical vectors** ("aliasing"), mostly because
`encode_option` captured *which card* acts but not **which Pokémon it targets** — so
"attach Energy to Mega Lucario" and "attach to a benchwarmer" looked identical to the
model, while the teacher's whole energy-placement logic differentiates them. Stage B:

- **Options now encode the target** (`inPlayArea`/`inPlayIndex` resolved to card
  features + an is-active flag). OPTION_DIM 53 → 90.
- **State now sees**: both discard piles (pooled), own discarded Basic Fighting Energy
  count (the teacher's Mega Brave attack scales on it), per-slot energy *type* counts,
  attached tools, status conditions, and the stadium. STATE_DIM 511 → 1,206.
- **New build gate** — `encoder_parity_check()` in `rl/gate.py`: walks a real game and
  asserts `rl/encoders.py` and `submission/main.py` encode every observation and option
  identically. The old weight-parity test fed random vectors, so it could never catch
  encoder *logic* drift — exactly the failure mode that becomes likely the moment
  encoders start evolving.

## Lessons learned

1. **Predict the loss before training, then verify.** Cross-entropy is `−ln(p_correct)`
   — a "surprise" score. An untrained net is ~uniform over N menu options, so its loss
   should be `mean(ln N)` ≈ 1.25 on our data. We measured 1.297 on the first batch:
   masking works, model behaves as theory says. (Also learned: `mean(ln N)` ≠
   `ln(mean N)` — averages don't commute through logs; the first prediction of "≈2.0"
   was that mistake.) ML fails *silently*, so this predict-then-verify habit is the
   cheapest bug-catcher there is.
2. **The overfit test is a diagnostic, not just a smoke test.** 500 samples wouldn't
   memorize past ~93% — which felt like failure until inspection showed 337/500 menus
   contained *indistinguishable options*. A model literally cannot separate identical
   inputs with different labels; the plateau measured our encoder's blindness, not a
   bug. That number became Stage B's design spec.
3. **Validate the success metric against reality.** The "≥95% vs random" gate assumed
   the teacher crushes random. Measured: the teacher itself only wins **88%**. You
   cannot clone your way above your teacher; the honest Stage A criterion was "match
   the teacher," which BC did. Measure the reference before trusting a target.
4. **Small samples flatter.** BC v0 read 91% over 100 games, then 81% over 300. A
   100-game win rate carries roughly ±3% *at best*; differences of a few points between
   agents are noise at that sample size. Decisions (ship/don't ship, better/worse) need
   300+ games or explicit error bars.
5. **Best-checkpoint ≠ last-checkpoint.** Validation accuracy peaked at epoch 5 and
   drifted down while train loss kept improving — textbook mild overfitting, and the
   reason the loop saves on val-improvement only.
6. **Two teacher instances, or corrupted data.** The sample agent keeps module-level
   state; self-play with one shared module interleaves the two players' globals. Loading
   two isolated module instances (`importlib`, distinct names) was required for clean
   demonstrations.
7. **Imitation accuracy and play strength are different metrics.** Stage B left val
   accuracy flat (90.9% → 90.4%) but raised the 300-game win rate 81% → 90%. The
   target-encoding fix didn't change how often the model matches the teacher's exact
   index (many aliased options were interchangeable anyway) — it changed *which
   mistakes* it makes: Energy now lands on the right Pokémon, and that wins games.
   Optimize the proxy, but judge on the outcome.
8. **Measure positional advantage before reading head-to-head numbers.** Player slot 0
   wins ~61% of teacher-mirror games in this engine, so any A-vs-B win rate carries a
   built-in slot bias. Fair comparisons need slot swapping (M2 TODO for `play_games`).

## Next steps — M2: self-play PPO

- Start from `bc_v1.pt` (policy *and* the value head, which was pre-trained on ±1
  outcomes this milestone precisely for this).
- Collector via the direct engine loop (measured ~1,000 games in ~8 min, single
  process); opponent pool {current, past checkpoints, teacher, random}.
- Success gate — calibrated per lesson 3 this time: **>50% vs the teacher over 300+
  games**, which BC alone cannot achieve (it can only match, never exceed).
- The ABILITY imitation gap (40% vs teacher's 100%) is a concrete thing PPO should fix
  on its own: firing the ability is free value, and self-play reward will find it.
