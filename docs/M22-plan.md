| difference between arms | n/arm needed | wall-clock at 2 arms |

| 15pp | ~175 | ~4–6 days |
| 10pp | ~390 | ~8–13 days |
| 5pp | ~1570 | ~5–10 weeks |

2pp apart. B2 vs B3 (2.0pp mirror, 3.5pp meta) is below anything this pipeline can adjudicate in
reasonable time — which is why the current live A/B may never resolve. Maximize expected
separation when choosing what to pair.

**No new slots needed to start:** B2 and B3 shipped 2.5h apart on 07-20 and are already accruing
as a rough pair. The pipeline can begin measuring them immediately.

   ship order at ρ=+0.991). Waiting fixes (2), not (3).

Team throughput is ~60–100 episodes/day **total**, split across active submissions.

## Sequencing constraint (read before reordering anything)

**Deck surgery invalidates every pinned baseline.** If we re-deck, `solver:lucario` stops being
the mirror and all M15–M21 comparisons break — the exact instrument problem M22a exists to fix.
So: fix the instrument → establish a live criterion → *then* consider deck changes. Any other
order and we cannot attribute the result.

## M22a — the pipeline (IN PROGRESS, 07-20)

**Built:** `rl/live_monitor.py` + `tests/test_live_monitor.py` (15 tests, suite 536 green).

```bash
uv run python -m rl.live_monitor status  --subs <ids> [--target 200]
uv run python -m rl.live_monitor compare --subs <a> <b> [--mde-pp 10]
uv run python -m rl.live_monitor cron    --subs <ids> --notify [--max-new 300]
```

The design property is **refusal**. `compare` emits a winner only when the observed gap exceeds
the MDE at the current n; otherwise it prints the n required and **exits 1**, so a cron job
cannot mistake "still accruing" for a result. It also refuses outright below n=30, where scores
are still the μ=600 opening prior decaying. The tests pin the refusal, not the reporting — the
M21 failure was a plausible number quoted without its power.

Current state (07-20): every pairing is unresolvable. B2 vs champion is a 7.7pp gap against a
**31.8pp** MDE at n=34/45; resolving it needs ~660/arm.

### Durable interface: `notebooks/m22_ab_monitor.ipynb` (cron dropped)

The cron approach was **abandoned** — a session cron dies with its Claude session and expires in
7 days, against a 4–22 day accrual. The notebook is durable, runs on demand, and *is* the handoff
artifact. Generated by `notebooks/build_m22_ab_monitor.py` (edit the `.py`, regenerate, reopen —
hand-editing `.ipynb` JSON is how cells silently break). Executed end-to-end, 0 errors.

| 3 | **power gate** — imports `live_monitor.compare`, so refusal cannot be bypassed |
| 4 | score over time (direct-labelled; required secondary encoding for the tritan pair) |

Shipping stays **manual** (cell 8, markdown only): a submission is irreversible, burns one of 4
daily slots, and competes for the episode throughput the arms need.

  better/equal/worse distribution, never a bare conversion rate. Report `n_unaffordable_dropped`.

  appearing equally in wins carries no information. Baseline every flag against the win side
  before it may motivate a leg.

  becomes the **generalization floor**; `rule:lucario` is **kept and relabelled** a

- **Label instruments honestly.** Head-to-head vs champion is valid for *progress* ("is this

## M22-live — turn accrual into a designed experiment

Current arms are B2/B3/champion, but **B2 vs B3 differ by 2.0pp mirror and 3.5pp meta — both
inside MDE.** The running experiment may be underpowered at the *treatment* level, so perfect
measurement could still adjudicate nothing. Hence a control arm that definitely differs.

Slot budget: **4/day**, 2 used on 07-20 (B2 06:13, B3 08:54 UTC).

- ~~Re-ship the M20 champion net~~ — **RULED OUT (Piotr, 07-20).** The ship-order confound
  therefore remains unaddressed; any future offline→live correlation must still be reported with
  the caveat that skill and calendar time are entangled in our sample.
- **Positive control `osv4_ei1b` (0.305), ~20pp below the shipped agents** — deferred, not
  rejected. Answers the binary question: *can live separate anything at all?* If it cannot
  separate 0.305 from 0.509, live is unusable at any n and we stop validating offline metrics
  against it.
   ⚠️ It does **not** give a clean offline→live slope: it is a different lineage (supervised
   relabel), so strength is confounded with failure mode. Same-lineage early checkpoints are
   clean but too tightly clustered to provide a lever arm.
   ⚠️ It burns ~25–33% of episode throughput on an agent guaranteed to lose, while B2/B3 are
   starved of exactly the episodes they need.
3. Set an explicit accrual **target and decision date**: ~150–300 games/arm. At 2 arms and
   current throughput that is ~4–8 days; each added arm extends it proportionally.

## M22c — the next shippable model (was M22b)

Justified by the one hypothesis that survived the power analysis: **PPO > BC**, Gate A kills at
18–26pp against a 7pp MDE. Extend B3's recipe from `ppo_current_m21legB3.pt`: longer legs,
KL annealed to 0, `plan-tau ≥ 1`, mixture-with-replay held **fixed** from B2/B3 so the leg varies
one thing. **Retire `--gust-boost`** (chased an artifact; never moved greedy-eval behavior, 0/217).

**DECIDED (Piotr, 07-20): `dragapult` stays OUT of the training mixture.** It is the only
opponent we own that is clean on *both* leakage and endogeneity — never in `collector.py`,
`plan_iter.py` or `ppo.py`, and authored by The Pokémon Company rather than by us. Training
against it spends a non-renewable instrument. It is reserved as the out-of-loop check on whether
M22b's PPO scaling generalizes beyond the closed loop.

Note a held-out *harvested* archetype (e.g. drakloak) is **not** an equivalent substitute — it is
still solver-piloted, so it fixes leakage but stays endogenous. Use it as a secondary
generalization check, not as a replacement for dragapult.

### 🐛 Fix the mixture double-count before launching any leg

B3's declared mixture contains `solver:.../deck_20dcd3130bc0.csv=0.30` **and**
`solver:lucario=0.15` — the same opponent (byte-identical deck, same pilot) counted twice, so
**45% of training was one opponent** while the config read as two at 0.30 and 0.15. The mirror
gate then measured exactly that opponent.

Before M22b: make `parse_pool` (`rl/collector.py:119-148`) deduplicate by *resolved* (deck, pilot)
identity — merge or reject duplicates rather than silently summing — and consciously reallocate
the freed mass. Any leg launched on the current config is training on a distribution nobody
intended.

**Baseline to capture (not urgent, but do it before M22b's result lands):** measure B2 / B3 /
champion vs `rule:dragapult`, n=400 × 2 seeds, workers 8. This establishes the out-of-loop
reference point that M22b's candidate will be compared against.
