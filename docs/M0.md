# M0 — "Watch it fight": the end-to-end pipeline

**Date:** 2026-07-07
**Status:** ✅ Complete — agent builds, passes all gates, plays full legal games, packaged for Kaggle (`pokemon-tcg-ai-battle`; the prize track `pokemon-tcg-ai-battle-challenge-strategy` is the longer-term target).

---

## What M0 was about

Before teaching an agent to play well, we proved that every pipe it will ever flow
through actually works. M0's deliverable was deliberately dumb: an agent with a
**completely untrained (random-weights) neural network** that nonetheless plays full,
legal games, loads the exact way Kaggle loads it, and ships as a one-command package.

The idea: get every non-learning problem (encodings, file formats, runtime quirks,
packaging) out of the way *now*, while the agent is trivial — so that from M1 onward,
"improve the agent" only ever means "produce a better weights file."

## What we built

**Data layer** (`deck_analysis.ipynb` → `data/`)
- Explored the 1,267-card database, categorized cards by the rules (Pokémon stages,
  Trainer sub-types, Energy; ex/Mega-ex/ACE SPEC/Tera overlays and their Prize values).
- Produced machine-ready tables: `cards_features.parquet` (one row per card, 36 numeric
  features) and `attacks_features.parquet` (per-attack costs/damage), plus a
  `validate_deck()` legality checker (60 cards, ≤4 copies by name, ≥1 Basic Pokémon,
  ≤1 ACE SPEC; Basic Energy exempt from the copy cap).

**The `rl/` package** (the "factory" — training side, torch allowed)
- `encoders.py` — turns a live game observation into a fixed 511-float state vector and
  each presented action into a 53-float option vector. Numpy-only by design.
- `policy.py` — `OptionScorer`: a small network that scores each presented option
  against the state (a "pointer" setup, since the number of legal actions changes every
  turn), plus a value head for later PPO training. `save_npz()` exports weights.
- `deck_search.py`, `eval.py`, `replay.py`, `gate.py`, `export.py` — deck mutations,
  game-running/win-rate helpers, replay saving + browser UI, pre-submission checks,
  artifact export.
- `bc.py`, `ppo.py` — documented stubs; that's M1/M2 work.

**The `submission/` package** (the "product" — what ships to Kaggle)
- `main.py`: copied encoder functions + a hand-written numpy forward pass. **No torch,
  no polars, no imports from `rl/`** — just numpy, the `cg` engine bindings (bundled
  *inside* the package, see lesson 8), and three data files (`policy_weights.npz`,
  `card_features.npy`, `deck.csv`).

**Tooling**
- `build_submission.ps1` — one command: export artifacts → run gates → package tar.gz →
  (optionally, with `-Message "..."`) submit via the Kaggle CLI. A failed gate aborts
  the build, so a broken or mismatched package cannot be produced.
- `replays/index.html` — auto-generated replay browser: win-rate table per matchup and
  a click-to-watch page per game (opens the official ptcgvis visualizer).

## Architectural decisions (and why)

| Decision | Why |
|---|---|
| **Engine (`cg.api`) as ground truth, CSV for humans** | The engine's typed data is exactly what the agent sees at runtime; the CSV is for readable exploration. Both share card IDs, verified identical (1,267 cards). |
| **Option-scoring ("pointer") network, not a fixed action head** | The game presents a *variable-length list* of legal options each turn. Scoring the presented options gives action masking for free. This one fact also ruled out… |
| **No RL framework (SB3/RLlib/etc.); hand-rolled PPO on PyTorch** | Frameworks assume fixed action spaces and Gym-style envs; ours is neither. CleanRL is our reference implementation, not a dependency. Torch chosen over the pre-installed JAX for debuggability and reference-code volume. |
| **Factory/product split: torch trains, numpy plays** | The submission is a frozen artifact with zero training dependencies. Every future improvement ships as new *data files* (`.npz` + `deck.csv`); `main.py` barely changes. |
| **Fixed deck until M3** | If the deck and the play policy change at once, win-rate movements can't be attributed. Play learning first, deck search later. |
| **Parity test as a permanent build gate** | The shipped npz is loaded back into torch and compared against the submission's numpy forward pass (agrees to ~1e-8). Silent train/serve skew is a classic ML failure mode; here it's structurally impossible to ship. |
| **Small network (≈500K params) on purpose** | Our input is engineered tabular features, not raw pixels — capacity isn't the bottleneck, game throughput is. Scale only when measurements demand it (the planned first upgrade is card *embeddings*, not depth). |
| **Logic in Python modules, shell scripts only orchestrate** | First draft embedded Python in PowerShell here-strings — unlintable, untestable, unreusable. Refactored into `rl/gate.py`; the .ps1 is ~30 lines of sequencing. |

## Lessons learned

1. **An untrained network is not a random player — it's an arbitrary *consistent* player.**
   Our M0 agent lost to the uniform-random baseline ~100% of the time, which felt
   impossible until we tallied its choices: offered the "attach Energy" action **1,439
   times, it took it twice**. Random initialization + greedy argmax = a fixed,
   systematically bad policy (it happens to "hate" the ATTACH encoding), repeated
   identically every game. Uniform random, meanwhile, attaches Energy constantly just
   because attach options dominate the action space — and beats the pacifist. This is
   the concrete motivation for *exploration* (sampling during training, entropy bonus
   in PPO): a deterministic policy can never discover that the action it avoids is the
   one that wins games.

2. **Kaggle doesn't import your agent — it `exec`s the file's source in an empty
   namespace.** Consequences: `__file__` doesn't exist (locate artifacts by *searching
   candidate directories for a known file*, not by assuming a path), and the runner
   picks **the last callable defined in the file** as your agent — so `def agent(...)`
   must stay last in `main.py`, forever. Testing with `env.run(["submission/main.py",
   ...])` (file path, not imported function) reproduces Kaggle's loading exactly and is
   part of the build gates for this reason.

3. **`env.render(mode="html")` is broken for this competition** — the pip package ships
   no JS visualizer, producing a page with a JavaScript syntax error. The supported
   path is the official web visualizer fed with `env.steps[0][0]["visualize"]`. Our
   replay pipeline embeds that JSON into self-contained local HTML pages.

4. **torch stores `Linear` weights as (out, in)** — the numpy port must transpose
   (`x @ W.T + b`). Also, layer names in the exported npz have gaps
   (`state_enc.0`, `state_enc.2`) because parameter-free ReLUs occupy the odd indices.

5. **Train/serve skew is the silent killer** — encoders are duplicated between `rl/`
   and `submission/` *by copy*, and the parity gate exists precisely because "the same
   preprocessing on both sides" is an invariant no one notices breaking.

6. **The engine allows one battle per process** (global state in the C library), so
   parallel self-play/evaluation will need `multiprocessing` with one environment per
   worker. Known constraint for M2's trajectory collector.

7. **Feature encoding is a hard ceiling on what can be learned.** The network cannot
   use information that never enters the state vector — e.g. today it can't see the
   discard pile, so it could never learn Mega Lucario's discard-scaling attack. "Data
   wrangling" isn't preprocessing trivia in RL; it defines the agent's perceptual world.

8. **The Kaggle agent runtime provides numpy but NOT the `cg` engine** — our first real
   submission died instantly with `ModuleNotFoundError: No module named 'cg'`. The
   official samples bundle the `cg/` folder *inside* the tarball (the runner adds the
   agent's directory to `sys.path`, which is how `import cg` resolves). Fixed by having
   `rl/export.py` sync `cg/` into `submission/` and the build script verify the archive
   contents. Two takeaways: (a) local gates couldn't catch this because the project
   root was importable — the build now also relies on an explicit package-contents
   check; (b) when a platform rejects your artifact, diff against the *official
   sample's packaging code* before theorizing.

## Next steps — M1: behavior cloning ("beat random")

Goal: replace the random weights with a policy *imitating* the rule-based Mega Lucario
sample agent. Success gate: **>95% win rate vs the `random` baseline.**

1. **Collect demonstrations** — wrap the sample agent in `rl.eval.RecordingAgent`, run
   a few thousand self-play games, store (observation, chosen action) pairs.
2. **Train `OptionScorer` supervised** (`rl/bc.py`) — encode each recorded decision,
   cross-entropy loss over the presented options with the teacher's pick as the label.
   Plain supervised learning; the gentlest first contact with torch training loops.
3. **Enrich the encoders first/alongside** — highest-leverage additions: discard-pile
   contents (see lesson 7), attached Energy *types* per Pokémon, tools, status
   conditions. The teacher uses discard counts; a student that can't see them plateaus.
4. **Re-run the option-type tally** (the ATTACH diagnostic from lesson 1) before/after
   training — the chosen-action distribution snapping toward the teacher's is the first
   direct evidence of learning.
5. **Export through the same pipeline** — `rl/export.py` starts loading the BC
   checkpoint instead of constructing random weights; everything downstream
   (gates, packaging, submission) is already built and unchanged.

Then M2: self-play PPO from the BC checkpoint, opponent pools, TensorBoard dashboard —
see `ARCHITECTURE.md` §4–5 for the full plan.
